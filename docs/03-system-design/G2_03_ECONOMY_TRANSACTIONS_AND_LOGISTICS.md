# G2-03 — Контракты экономики, инвентарей, производства, денег и перевозок

**2026-11-18 · DRAFT / NOT FROZEN**  
**Основание:** [GDD-03](../02-game-design/GDD_03_ECONOMY_PRODUCTION_LOGISTICS.md), [GDD-02](../02-game-design/NPC_POPULATION_AND_BEHAVIOR_GDD_02.md), [D-002/D-005/D-022–D-026/D-028/D-047](../../DECISIONS.md), [G0 производственные цепочки](../01-legacy-audit/VIME_PRODUCTION_SCIENCE_LOGISTICS_PASS_02.md). Исторические значения производительности, банковского процента и зданий могут расходиться между версиями; ни одна сумма не принимается как баланс до отдельного утверждения.

## 1. Типы экономической ценности и ответственности

| Тип | Природа | Допустимые операции |
|---|---|---|
| `PhysicalItem` | Реальные Minecraft предметы, связанные с собственником и местонахождением/контейнером | Получить, переместить, продать, использовать в рецепте |
| `Coins` | Деньги, учитываемые по счетам | Уплата, перевод, налог, оплата труда, *явно разрешённая* эмиссия/погашение |
| `Hammers` | Строительные очки города/государства | Только источник/расход, указанный в утверждённом рецепте |
| `Science` | Исследовательские очки | Утверждённое исследование/космическая миссия после prerequisite |
| `TradeStatus` | Не обязательно физический предмет: ресурсные торговые права/эффекты | Получить/потерять по правилам конкретного источника |
| `StockCapacity` | Складская вместимость в определённом месте | Резервировать, освободить, подтвердить |
| `WorkTime` | Ограниченный доступный труд работника | Назначить, отработать, восстановить отдыхом |

Значения не преобразуются автоматически: например, молоточки не равны железным предметам, монеты не создают хлеб без продавца/действительной поставки. В G0 старые сооружения могут производить виртуальные Hammers/Science; физическая работа NPC в Reborn **представляет действие производственного здания**, а не второй таймер выдачи того же результата (D-025).

## 2. Агрегаты и роли

| Aggregate | Кандидатные данные | Владелец |
|---|---|---|
| `StockLot` | `LotId, ItemKey, Quantity, OwnerId, LocationRef, Available, Reserved, Version` | InventoryLedger |
| `Reservation` | `ReservationId, OperationId, LotId/AccountId, Amount, OwnerId, Purpose, State` | ReservationService |
| `ProductionOrder` | `OrderId, RecipeId, BuildingId, JobId, InputReservations[], OutputCapacityReservation, Progress, State` | ProductionService |
| `Shipment` | `ShipmentId, CargoLotRefs[], FromRef, ToRef, CarrierId?, Route, RiskPolicy, State, DeliveryTime, Version` | LogisticsService |
| `MoneyAccount` | `AccountId, OwnerId, Currency, Balance, Version` | MonetaryLedger |
| `JournalEntry` | `EntryId, OperationId, DebitAccount, CreditAccount, Amount, SourceType, LogicalTime` | MonetaryLedger |
| `ResearchAccount` | `PolityId, ScienceBalance, Revision` | ResearchService G2-05 |
| `BuildCreditAccount` | `SettlementId/PolityId, HammersBalance, Revision` | Construction G2-04 |

`StockLot` логически связан с **реальным** существующим предметом/контейнером; сама запись склада не создаёт физический блок/стак. Если кто-то может изменить Minecraft-контейнер извне, требуется adapter reconciliation, а не вера в старую запись.

## 3. Фундаментальные операции над предметами

### STOCK-01 — принять реальную добычу/производство

**Input:** `OperationId`, `SourceRef` (дерево, ферма, шахта или рецепт), `ItemKey`, `Quantity`, `DestinationRef`, `Actor`.

**Preconditions:** разрешённый доступ к источнику, фактически добываемый объём/ресурс, допустимая ёмкость выхода, подтверждённая стоимость труда/износа/времени, отсутствие уже committed OperationId.

**Commit:** реальный источник потреблён/изменён согласно операции; у нового StockLot есть происхождение и один получатель; журнал создаёт единственный выпуск.

**Failure:** источник изменился между snapshot и commit; нет прав; контейнер полон; virtual/loaded конкурируют за одно дерево → один успешный коммит, второй `STALE_REVISION/INSUFFICIENT_SOURCE`; никаких двух единичных наград.

### STOCK-02 — зарезервировать и выдать

`AVAILABLE → RESERVED → IN_TRANSFER/CONSUMED/RELEASED`. Резерв **не** равен списанию из мира. Контракт `ReservationId` связывает конкретную партию и операцию. Перевод/потребление обрабатываются один раз; повтор после crash по тому же OperationId возвращает прежний результат.

**Conservation:** `OpeningBalance + VerifiedProduction + ExternalImport - VerifiedConsumption - AuthorizedLoss - Export = ClosingBalance` для каждой `ItemKey` внутри рассматриваемой хозяйственной области, включая cargo in transit. `ExternalImport` требует реального поставщика/события, не «деньги AI».

## 4. Производство и труд

### PROD-01 — запланировать производственную цепочку

1. Проверить существование, активное состояние и законную собственность здания.
2. Подтвердить, что `RecipeId` утверждён и версия определена, а не UNKNOWN из исторической wiki.
3. Проверить технологии, рабочий участок, права, StockLot, доступность работника и ёмкость получателя.
4. Зарезервировать входные товары, оборудование, JobId и будущий выход.
5. Записать `ProductionOrder RESERVED` и `ExpectedRevision`.

**Без подтверждённого рецепта:** `UNSUPPORTED_CONTENT`; не создавать искусственную «рыночную продукцию» из воздуха.

### PROD-02 — работа и финализация

- **States:** `CREATED → VALIDATED → RESERVED → RUNNING → READY_TO_COMMIT → OUTPUT_POSTED → COMPLETE`; отмена/ошибка имеют определённые этапы компенсации.
- **Executor:** JobService/G2-01; физический NPC в загруженной области либо виртуальная машина той же задачи вдали. **Не** два разных таймера производства.
- **Progress:** логическое активное время мира, наличные инструменты/входы, производительность, принятые GDD/G2 modifiers, без невидимого AI-бонуса.
- **Commit:** source inputs списаны ровно один раз; выход создан и зарегистрирован через STOCK-01; расход/начисление Hammers, Science, TradeStatus — только если это прямо указано в утверждённом RecipeDefinition.
- **Failure:** нехватка материала/переполненный склад/отмена/разрушенная мастерская/worker lost. При частично потраченных входах отсутствует право полной бесплатной компенсации — по будущему конкретному `RecipeFailurePolicy`, пока значение `TBD`.

### Дизайн совместимости старого CivCraft

В старой вики фермы и коттеджи могли иметь автономный доход, шахта — выдавать Hammers вместо кирки. Если NPC обслуживает здание Reborn, `ProductionOrder` — **один** источник итоговых товаров; исторический таймер заменяется executor модели, не запускается параллельно. Путь переноса конкретного здания/рецепта требует source-version карточки из G0.

## 5. Деньги и платёжные операции

### MON-01 — перевод

- **Actor:** игрок, NPC работодатель, город, государство или предприятие с законным правом тратить средства.
- **Preconditions:** счёт существует; достаточно доступного остатка после резервов; у получателя валидный AccountId; платежный тип разрешён.
- **Reserve:** конкретная сумма в исходном счёте под `PaymentId`.
- **Commit:** сбалансированная двойная запись (`Debit/Credit`) внутри денежной книги; отправитель теряет, получатель получает **ту же сумму**; каждая `OperationId` отражается однократно.
- **Failure:** устаревшая ревизия, отказ получателя, недостаток средств → резерв освобождён, оба счёта остаются непротиворечивыми.

### MON-02 — законная эмиссия/погашение

Создавать/уничтожать Coins может только заранее определённый `MonetarySourcePolicy` с отдельным системным контрсчётом и проверяемым событием. `SourcePolicyId`, лимит и величина — **NOT APPROVED**; никакой AI-город не может «подкрепить бюджет» неограниченными деньгами. Для finite/sandbox — одна и та же политика.

### MON-03 — зарплата, налог, торговля

Зарплата: действительный трудовой договор → проверка выполненных работ → удержание суммы по MON-01 → доход работника. Городские и государственные налоги применяются к отдельным юридически определённым налоговым базам, один раз по ревизии действующей ставки. Торговая сделка — обмен денег **и** StockLot собственности по одному `TradeId`; частично исполненная продажа имеет запись долга/ожидания или компенсации, не выдаёт товар бесплатно.

**OPEN:** налоги, ставки, банковские проценты (G0 `BANK-CONFLICT-001`), места эмиссии, источники ренты, механизм банкротства/долгов.

## 6. Логистика физическая и виртуальная

### SHIP-01 — инициировать отправку

**Inputs:** `ShipmentId`, `ActorId`, `From`, `To`, `CargoReservations`, `RouteRef`, `Carrier`, `ExpectedRevision`.

**Checks:** отправитель реально владеет товарами либо уполномочен распоряжаться; получатель может принять; маршрут допустим по правам/границам; вместимость/стоимость/время/риск не нулевые по неопределённой халявной формуле; конечный StockCapacity зарезервирован.

**State:** `REQUESTED → RESERVED → IN_TRANSIT_LOADED/IN_TRANSIT_VIRTUAL → DELIVERY_PENDING → DELIVERED`; `FAILED/LOST/RETURNING` — отдельные исходы. Два типа IN_TRANSIT никогда не действуют одновременно.

**Commit:** в момент отправки StockLot находится **в грузе**, не на складе отправителя, а при доставке только в складе адресата. Права собственности могут измениться по контракту продажи на согласованном этапе, не по одному лишь физическому приближению. При поражении каравана lost cargo не восстанавливается одновременно как новый трофей и у прежнего владельца.

### SHIP-02 — LOADED↔VIRTUAL

`ShipmentId`, logical progress, cargo quantity, carrier identity, route revision and risk state остаются теми же; видимая сущность лишь проекция. Время/провозная способность/износ не улучшаются при выгрузке чанка. Обратный переход материализует **тот же груз**, а не второй.

**Failure cases:** смена владельца города во время пути, уничтоженный receiving warehouse, таймер завершился в момент materialization, игрок вскрыл физический контейнер, сервер упал после доменной доставки до spawn отображения — требуется `RECONCILIATION_REQUIRED` без двойного товарного результата.

## 7. Комбинированный сценарий мастерской

`Право на участок → аренда → MON-01 оплата → STOCK-02 покупка сырья → JOB-01 назначение NPC → PROD-01/02 изготовление → SHIP-01 доставка → MON-03 продажа/налог → обновление ledger`.  
Действует для NPC и player-run предприятия (D-047), без автоматических государственных полномочий. Каждый этап показывает источник, причину отказа и действительный юридический owner; в P1 нельзя выдавать незавершённый бизнес-цикл за готовую фичу.

## 8. Аудит и reconciliation

- `OperationId` и `JournalEntry` позволяют найти цепочку причинно связанных расходов, но *не гарантируют* единый атомарный commit во всех Minecraft API.
- `InventoryDiff`: авторитетный доменный груз vs реально доступный сундук/инвентарь; найденное расхождение должно блокировать дублирующую выдачу и запускать согласованное исправление/ручной admin case.
- При перезапуске process `READY_TO_COMMIT` и `DELIVERY_PENDING` не начисляет результат второй раз.
- Проекты эмиссии и налоговых коэффициентов нельзя реализовывать, пока они имеют статус OPEN.
