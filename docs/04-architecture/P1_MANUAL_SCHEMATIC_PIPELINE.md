# P1 — ручное создание эталонных схем для CivCraft

**Дата:** 2026-11-19 · **Решение:** заменить авторскую строковую 7×7×6 сетку `CampHeartTemplate.LAYERS` на вручную построенный игроком эталон Minecraft. **До получения и интеграции реального NBT старый шаблон остаётся действующим.**

## Действия автора схемы (Minecraft Java 26.3)

1. Создать отдельный тестовый мир с Creative и разрешёнными командами.
2. Построить здание вручную, включая двери, окно, все ступени, плиты, фундамент и полноценный вход.
3. Выполнить `/give @p minecraft:structure_block`.
4. Поставить структурный блок за пределами здания, выбрать **Save**, задать имя `civcraft_reborn:camp_heart_v2`.
5. Установить смещение и размер выделенной области, охватывая только постройку, затем сохранить её в файл **.nbt** на диск (не только в память).
6. Найти `<папка мира>/generated/civcraft_reborn/structures/camp_heart_v2.nbt` (если нет, проверить соседнюю `structure`), передать файл разработчику. Включить общий скриншот четырёх сторон здания, если нужно согласование внешнего вида.

## Техническая интеграция в мод (отдельный обязательный следующий коммит после получения файла)

- Источник истины: один NBT с палитрой `BlockState`, координатами и размерами. Загрузчик работает **на сервере** из ресурсов мода, отдаёт **то же самое определение** клиентской проекции; нет дублирующихся ручных матриц.
- Для первого лагеря привязка к стартовому предмету не требуется: он только запускает проект. Независимый `origin` здания, смещение Y и поворот 90° остаются в `CampHeartSite`.
- Поведение воздуха нужно выбрать явно: обычные воздушные ячейки внутри bounding box могут либо игнорироваться, либо требовать расчистки. Для дома важна отдельная маска обязательного воздуха в дверных проёмах/интерьере. **Пустоту нельзя бездумно считать требуемым блоком**.
- Валидация обрабатывает не только идентификатор, но и важные свойства `BlockState`: ось бревна, направление и half двери, тип плиты, facing и half лестниц, подключение стеклянных панелей учитывать как производное состояние соседства.
- Дверь требует одного предмета, но двух BlockState; корректный расход и производительность списка материалов считаются из NBT. Учёт повёрнутых на 90° лестниц/дверей должен происходить одинаково на сервере и клиенте.
- Ведомость материалов, прогресс `X/N`, цветная полупрозрачная голограмма и команда диагностирования расхождений получают данные **из одного NBT**. Хардкод `162` должен исчезнуть из игровых сообщений и тестов после миграции.
- Старые подтверждённые проекты должны сохранить свой `blueprintId` и не меняться молча при обновлении шаблона. Нужна версия чертежа, например `camp_heart_v1` и `camp_heart_v2`, и определённая политика миграции.
- Учитывать авторские права при использовании чужих строений: эталон пользовательский или лицензированный.

## Критерии приёмки

1. Загруженный NBT можно вернуть в отдельном тестовом мире в точности теми же блоками и ориентацией.
2. Голограмма по NBT совпадает с эталоном; поворот/вертикальный перенос не меняют состав.
3. `inspect` и экран проекта сообщают одинаковый прогресс; первые расхождения выдают фактические координаты.
4. С реальной корректной постройкой проект достигает 100%, уведомляет о готовности и позволяет `Основать лагерь` отдельным действием.
5. Существующие миры со схемой v1 не получают незаметно геометрию v2.

**Статус:** автономный импорт .nbt в проверенный промежуточный JSON реализован. Загрузка этого JSON самим модом и замена старого шаблона пока не реализованы: потребуется эталонный файл и политика миграции.

## Инструмент импорта (реализован)

Запуск в PowerShell из корня репозитория:
    python scripts/import_structure_nbt.py camp_heart_v2.nbt --id camp_heart_v2 --output src/main/resources/data/civcraft_reborn/blueprints/camp_heart_v2.json
    python scripts/test_import_structure_nbt.py -v

- Обычный и gzip-сжатый Minecraft Java Structure NBT; только стандартная библиотека Python.
- Сохранение block ID, свойств BlockState (facing, half, axis и т.д.), точных координат и размеров.
- Валидация палитры, повторов, границ, небезопасных блоков и неразрешённых данных block entities.
- По умолчанию воздух пропускается; --require-air включает явные воздушные позиции в чертёж.
- Формат выхода: civcraft_reborn:blueprint/v1, id, size, cells, required_cells и сводка блоков.
- Ведомость считает позиции BlockState, а не расход предметов: дверь занимает две позиции, но один предмет.
- Регрессионные тесты выполняются в GitHub Actions до Gradle.

Ограничение: JSON — промежуточный результат, пока не загружаемый модом. Старые проекты продолжают использовать шаблон v1. Для изменения нужен эталонный .nbt и отдельная интеграция в runtime.


## Реализация каталога чертежей (P1.1)

Сейчас построение эталона в творческом мире и импорт в рабочую сборку устроены так:

1. В Minecraft Java 26.3 сохранить собственное здание через Structure Block в `.nbt`.
2. В корне репозитория выполнить:
   ```powershell
   python scripts/import_structure_nbt.py "C:\\path\\to\\camp_heart_v2.nbt" --id camp_heart_v2 --output src/main/resources/data/civcraft_reborn/blueprints/camp_heart_v2.json
   ```
3. Конвертер сохраняет JSON со всеми позициями и свойствами BlockState, а также автоматически дополняет `src/main/resources/data/civcraft_reborn/blueprints/index.json`.
4. Пересобрать мод. Для сетевой игры **обновить JAR и сервера, и клиентов**: схематика хранится в ресурсах мода и должна быть одинаковой на обеих сторонах.
5. Поставить основание лагеря, открыть G → Схема строительства → Сердце лагеря. В окне размещения выбрать `Вариант: camp_heart_v2` **до подтверждения**.
6. Разместить через F7, подтвердить участок, физически построить дом, открыть `Проверить постройку` и дождаться X/X. Кнопка `Основать лагерь` станет доступной только после серверной проверки.

Ключевое условие: `CampHeartSite.blueprintId` хранится в SavedData; старые стройки автоматически получают `camp_heart_v1`. Выбор новой схемы после подтверждения запрещён — обновление мода не должно менять игроку уже построенный объект.

Сервер проверяет позиции, блоки и свойства по выбранному JSON; клиент рисует голограмму из того же ID. Размеры больше не ограничены 7×7×6, однако сам стартовый предмет и начальный радиус планирования остаются текущими правилами P1.

**Ограничение:** прямой импорт `.nbt` через игровой GUI без пересборки JAR пока отсутствует. Это следующий удобный пользовательский сценарий и не является частью подтверждённой реализации. Пользователь должен предоставить реальный эталонный `.nbt` перед выпуском замены старой схемы.

**Приёмка:** обязательны проверки вариантов разных размеров, ручной расстановки и поворота блоков, прозрачности клиента и полного строительного цикла. CI проверяет компиляцию, юнит-тесты и запуск сервера, но не доказывает корректное изображение Minecraft.
