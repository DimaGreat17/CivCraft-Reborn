# P1 / 0.2 — Camp founding and first physical Camp Heart: vertical slice

**Date:** 2026-11-19
**Status:** detailed design proposal for implementation; implementation NOT complete
**Applies to:** player-founded camp, before recruitment and builder automation
**Related:** `P1_PLAYER_BUILDING_FOUNDATIONS.md`, `P1_GAME_START_AND_BUILDERS.md`; PR #7 and issue #8.

## Fixed design decisions (owner-approved)

1. The player spawns in a living world and may either join an existing inhabited settlement or found their own. This document covers the second route only.
2. Founding starts by **crafting and placing a special Camp Heart foundation block** in a CivCraft-enabled world.
3. Placing that block reveals a **full-sized moveable/rotatable 3D schematic of a complete functional Camp Heart building**. The placed block is a real anchor incorporated into the future building.
4. Before confirmation the schematic moves and rotates, but the foundation block remains placed in the world. The server validates the final footprint.
5. The first Camp Heart is **built entirely by the player manually using real Minecraft blocks**. There is no initial builder workforce and no hammer production requirement for this first structure.
6. Correctly placed blocks replace individual holographic positions; real progress is checked server-side, persists and decreases if a required block is removed.
7. A completed Heart unlocks founding/management of an actual Camp. **The Camp Heart is a functional full building**, not a single core plus an obsidian cross.
8. Later buildings use their own foundation items and the same physical schematic pipeline. After the camp is operational and recruits workers, numerical hammer production allocated to construction orders allows **gradual real block-by-block automatic construction**, subject to actual material availability.

## Proposed starter Heart design — NOT yet balance-locked

- First iteration: compact **7×7 footprint, maximum height 6** (dimensions relative to confirmed schematic origin). This is a proposal pending a precise BlockState schematic.
- Style: early survival rustic timber-and-stone administrative hut, small enough to build by hand. No precious resource gate by default.
- Include wood/stone floors, walls, entrance, roof, internal control/foundation point and enough airspace to use the structure; no automatic residents, beds, storage, workshops or other free facilities.
- Materials must be generated by counting the real versioned schematic, not a guessed fixed list. Recommended accessible materials: logs, planks, cobblestone, wooden stairs, door, window glass.
- Whether the historical **four obsidian per Camp Core placement** grant is retained, changed or removed is a **separate balance/migration decision**. Do not silently delete previously chosen reward behavior or make it a finished-building requirement by default.
- Server structures should be defined by a versioned data model of exact relative positions, expected BlockState/block-family predicates, placement dependency order and optional visual build phase. Orientation-sensitive blocks (stairs, doors, etc.) need rotated state validation.
- Minecraft multi-block structures must validate both halves/parts correctly.

## Player experience / UI contract

### A — acquire and place

- Craft a `civcraft_reborn:camp_core` (existing registered ID, visual name may become «Основание лагеря» without migration-breaking ID rename).
- In a CivCraft-enabled world, place on suitable supporting terrain.
- On successful placement, the server creates pending `BuildingId` / `ConstructionOrder`, not an active Camp, and opens the positioning UI.
- In other ordinary Minecraft worlds, placement must not silently create a functioning CivCraft camp; opt-in checks govern registration.

### B — position and confirm

- Full 3D projection visible with placement validity coloring. Player can shift the projected building by blocks horizontally and rotate ±90°. Foundational anchor remains fixed and must belong to the final footprint.
- Show errors: out of world border, existing claimed site / another building, overlap with protected solid blocks or reserved structures, unsupported footprint, missing rights, unloaded target chunks.
- Prior to confirmation allow cancel and recover the pending placement safely. **No automatic copying/moving other physical blocks.**
- On confirm, server persists selected schematic identifier + version, transformed origin and rotation, footprint, player owner and world dimension. The client is not authoritative.
- After starting physical construction, ordinary UI reposition is disallowed unless a separate safe rebuilding/cancel path is designed.

### C — manual construction

- In-world hologram displays missing block states; inventory material summary shows `required / correctly placed / carried / missing`.
- Player places real blocks in the world with vanilla inventory costs. Existing matching blocks inside the approved schematic count toward progress; never silently replace owner blocks or force clear unrelated blocks.
- Client display updates promptly, but server performs actual completion checks.
- Per-block progress = validated required positions / required positions count. For things like doors, count atomic multiblock requirements as logically valid units to avoid misleading 100% readings.
- Wrong, missing or removed blocks are listed as errors and do not qualify for activation.
- On disconnect/restart or unloaded chunks, preserve construction order; unloaded data cannot be treated as verified completed.

### D — complete and found

- Only when all compulsory physical positions/room and control-block criteria pass does the structure enter `PHYSICALLY_COMPLETE`.
- The **global Camp / Civilization menu** is opened by a dedicated on-screen button (and a configurable keybind on desktop), never by right-clicking the Camp Heart block. This menu exposes a separate **«Основать лагерь»** action. Server verifies unchanged building/rights/world restrictions and creates a persistent CampId, owner membership and initial CAMP stage atomically. Prevent duplicate founding by retry.
- Then `ACTIVE` enables camp management, naming, building catalog and recruitment prerequisites. The founding action should be idempotent; interrupted save/restart must not duplicate CampId.
- First inhabitants are not created out of thin air; invitations/recruitment require real eligible residents and actual housing conditions.
- Destruction of required parts of an ACTIVE Heart marks it damaged and temporarily suspends dependent functions, with a recovery path after rebuilding. Existing CampId persists; do not automatically delete a civilization or orphan citizens due to one missing block.

## Initial UI states

- `FOUNDATION_PLACED` — physical anchor exists; placement menu opens.
- `POSITIONING` — can move/rotate; construction site not confirmed.
- `BUILDING_MANUAL` — fixed layout, live material and block progress, ghost projection.
- `PHYSICALLY_COMPLETE` — all construction checks green; founding available.
- `ACTIVE_CAMP` — permanent CampId and management UI.
- `DAMAGED` / `SUSPENDED_UNLOADED` / `INVALID_SITE` — explicit warnings and safe repair/resume; never silently call an incomplete building finished.

## Server identity / security

- Scope by world UUID + dimension + BuildingId; optional CampId before formal founding and permanent CampId after.
- Prevent duplicate active founding in restricted sites, cross-world contamination, forged client completion signals, false inventory progress and overlapping construction claims.
- Use authoritative block state checks, occupancy, world border and chunk-loaded checks.
- Existing 96-block separation in prototype is **legacy/provisional**; align with canonical territorial design before locking the value.
- Persist schema and migration story for existing CampSavedData, old isolated Camp Core and previous HEART cross; no destructive silent conversion.
- No graphical render-upload hacks: previously observed `StagedVertexBuffer.upload` inside an active render pass caused a confirmed client crash. Test corrected projection on a real client.

## Concrete acceptance scenario — minimal first playable loop

1. New disposable CivCraft world. Player obtains legitimate recipe materials and crafts camp foundation block.
2. Places it: full Heart ghost appears; only the anchor is physically present; camp management is not active.
3. Moves and rotates projection, verifies collision error, confirms a valid footprint.
4. Sees exact material list and starts constructing manually.
5. For each correctly placed test block, ghost disappears and server progress rises. Incorrect block does not count; breaking a valid block decreases progress.
6. Save/restart: confirmed placement, per-block construction and ownership survive.
7. Complete all physical structure blocks; check status becomes physically complete.
8. Use «Основать лагерь», choose name, confirm active CAMP identity; trying before complete is rejected.
9. Open real management UI via its dedicated HUD button; see camp identity and new building options. Try to recruit NPC: no free residents, actual housing and existing NPC are still required.
10. Break a compulsory Heart block: diagnostics flag damaged; restore block: active functions resume without new CampId or duplication.
11. Test 2-player authorization, invalid dimensions, unloaded chunks, dedicated-server bootstrap, actual client renders and known STORAGE schematic regression.

## Implementation plan (ordered)

1. Author **exact versioned Camp Heart schematic**, block-state transforms and count-derived material bill. Hold final art and crafting costs pending approval.
2. Create persistent construction-site server model and fixed-world placement transactions (reusing `CampCoreBlock`, `BlueprintTransform`, `BlueprintNetworking` and placement UI as safe).
3. Implement manual-progress authoritative validator and materials screen for the full Heart.
4. Gate `/civcraft camp found` and GUI founding on physically complete Heart, with durable CampId and recovery.
5. Client GUI/renderer test + restart/multiplayer tests and CI. Do **not** merge development PR #7 or claim release before acceptance.
6. Only then connect recruitment and numerical-hammer-based automatic builders in a later vertical slice.

## Unresolved design choices requiring explicit later agreement

- Exact 7×7×6 blueprint geometry and full BlockState list, final appearance and craft recipe.
- Whether the player can dismantle/cancel a partially built heart, and return/reuse its special foundation item.
- Obsidian placement reward / exploit behavior; no silent replacement of existing rule.
- Naming flow and founding cost, initial claim radius / 96-block rule, joining/ownership and claim boundaries.
- Whether to permit prebuilt matching world blocks to count; recommendation above says yes only inside approved footprint with full permissions.

## Confirmed UI access decision (2026-11-19)

- The overarching **Camp / Civilization menu opens from a dedicated HUD button**. On desktop a rebindable hotkey may provide the same action. Access must not depend on proximity to the Camp Heart, its visibility or its right-click interaction.
- Before founding, that menu presents available founding-site / construction status and locked civilization controls; after founding, it shows authorized camp management and progression.
- The Camp Heart block remains the physical structure anchor, not a required UI trigger. Construction-site details and blueprint controls can be entered from the global menu.
- The server still validates ownership, membership, distance-sensitive physical construction actions and permissions; opening a screen does not grant authority.
- Prior prototype UI activated from Camp Core right-click is **superseded** and must be refactored during implementation.
