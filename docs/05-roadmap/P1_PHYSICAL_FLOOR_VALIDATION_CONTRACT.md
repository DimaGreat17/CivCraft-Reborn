# P1 — PHYSICAL: пригодность пола по реальной геометрии и проходимости NPC

**D-057 APPROVED_CONCEPT, 2026-11-18.** Игрок утвердил распознавание пригодного пола **по реальной физической проходимости и безопасности поверхности для NPC**, а не только полным блокам или жёсткому списку типов. Технический контракт ниже — **PROPOSED / NOT FROZEN**; не является реализованным кодом.

## 1. Совместимость с решениями

- D-053 ROOM: кровать, укрытие, достижимый вход и безопасность.
- D-054 COMBINED: вместимость ограничена пригодным полом и кроватями; комфорт — отдельная метрика.
- D-055 FLOOR: измеряется полезная площадь пола, не объём воздуха.
- D-056: **предварительная** норма 4 пригодных блока² на NPC, подлежащая тестированию.
- D-057 PHYSICAL: физические коллизии/опорная поверхность, допустимость движения и безопасность определяют, засчитывается ли участок пола; полный блок не обязателен.

## 2. Физическая пригодность — проектные условия

**Для каждой кандидатной поверхности** сервер проверяет:
1. **Опору:** игровая геометрия в данной позиции действительно поддерживает габариты NPC; нельзя засчитывать пустоту или неустойчивую поверхность.
2. **Размещение:** коллизии позволяют персонажу стоять и занять положение без застревания, вредного контакта или невозможного перекрытия.
3. **Маршрут:** поверхность реально достижима из связанной жилой зоны и доступной точки использования кровати; одиночный безопасный островок внутри закрытого объёма не даёт площадь.
4. **Безопасность:** проверяется фактический вред (огонь, опасные жидкости/блоки, падение и прочие условия), а не только название предмета. Точные пороги открыты.
5. **ROOM и права:** эта поверхность относится к проверенному помещению и доступна законно; не захватывает чужую территорию и не дублируется между помещениями.

**Важно:** в текущей проектной модели «физическая проходимость» — проверяемый критерий, но не обязательное моделирование полного пошагового передвижения NPC на каждой перепроверке. Конкретная оптимизация должна сохранить эквивалентность фактической игре.

## 3. Плиты, ступени и нестандартные блоки

| Пример | Принцип | Что остаётся уточнить |
|---|---|---|
| Полный твёрдый блок | Может входить в пригодную площадь, если безопасен и достижим | Коллизии, возможная блокировка сверху |
| Нижняя/верхняя плита | Может учитываться при безопасной опоре и доступе; не запрещена по типу | 1 клетка или дробная площадь; зависимость от высоты |
| Ступень | Может учитываться, если NPC действительно может по ней перемещаться/стоять | Как измерять неоднородную горизонтальную поверхность |
| Ковёр на поверхности | Сам по себе не добавляет второй слой полезного пола | Как читать объединённую геометрию |
| Лестница или переход между этажами | Разрешённая физическая связь, не автоматически дополнительные квадратные блоки | Учитывать ли зону прохода как жилую площадь |
| Модовый блок с коллизией | Может учитываться при достаточных физических свойствах | Совместимость с модовыми collision shapes |
| Люк, забор, жидкость, опасная поверхность | Не определяется лишь whitelist/blacklist; фактическая проверка | Статические/динамические состояния, жидкости и риск |

Для плит и ступеней **нет утверждённого правила присваивать всегда 1 блок²**; это отделённое балансно-геометрическое решение. Не считать один и тот же физический участок несколькими ячейками из-за дробных высот.

## 4. Предложение по алгоритму серверной проверки

1. Изменение кровати или релевантного блока локально инвалидирует запись помещения; глобальный поиск домов каждый тик запрещён.
2. Система выбирает ограниченную область вокруг валидной кровати и определяет физические кандидаты пола, используя коллизии и габариты NPC.
3. Строит ограниченную связность через реально допустимые переходы с проверкой препятствий и опасностей; учитывает этаж Y, лестницы, двери, права.
4. Сопоставляет поверхности с единственным `RoomId/HousingRegionId` и единственным владельцем площади; общие коридоры не дублируются.
5. Возвращает `VALID / INVALID / PENDING_VERIFICATION` и причины отказа. Недоступные чанки, устаревшая ревизия и превышение лимита обхода **не** увеличивают площадь.
6. После успешной проверки пересчитываются FLOOR-площадь и предполагаемая COMBINED-вместимость из реальных кроватей; комфорт остаётся независимым.
7. Перезапуск/сбой восстанавливает записи, ревизии и связи с назначенными CitizenId; повторная проверка не создаёт второе жильё и не клонирует предметы.

### Предлагаемый контракт

`FloorSurfaceRef(WorldId, BlockPos, SurfaceKey)`, `CollisionSnapshotRevision`, `WalkableFootprint`, `SafetyResult`, `ReachabilityRegionId`, `HousingRegionId`, `EligibleAreaContribution`, `ReasonCodes[]`.

**НЕ утверждены:** структура классов, тип обхода и pathfinding Fabric, горизонтальная/наклонная площадь, округление неполных клеток, допуск по высоте, бюджеты сканирования/нагрузки. До их согласования нельзя считать систему реализуемой в фиксированном объёме работ.

## 5. Примеры отказов игроку

«Нет опоры», «Не хватает места для прохода», «Поверхность опасна», «Недостижимо из жилой зоны», «Площадь уже закреплена за другим помещением», «Часть помещения недоступна для проверки».

Нельзя сообщать «жильё пригодно» только по клиентской визуализации; решение принимает сервер.

## 6. Проверки P1 для PHYSICAL

| ID | Сценарий | Ожидаемое свойство |
|---|---|---|
| PHYS-01 | Безопасный пол из полноразмерных блоков | Считается при выполнении остальных условий |
| PHYS-02 | Безопасный проход/пол из плит | Не исключается по одному только типу блока |
| PHYS-03 | Проходимые ступени | Проверяются фактические коллизия и достижимость |
| PHYS-04 | Небезопасная поверхность того же типа | Не засчитывается из-за опасности |
| PHYS-05 | Формально «пол», но перекрыт объём для NPC | Не даёт площадь |
| PHYS-06 | Отдельный недостижимый островок пола | Не увеличивает пригодную площадь |
| PHYS-07 | Ковёр поверх пола | Не удваивает площадь |
| PHYS-08 | Два уровня в одной X/Z позиции | Учитываются только как отдельные физически достижимые этажи без двойного счёта |
| PHYS-09 | Изменение положения люка/двери/ступени | Вызывает обоснованную локальную перепроверку |
| PHYS-10 | Модовый блок с нестандартной collision shape | Обрабатывается геометрически, безопасный отказ при неизвестном состоянии |
| PHYS-11 | Другая комната претендует на ту же поверхность | Только одна область получает кредит площади |
| PHYS-12 | Граница незагруженного чанка | Без принудительной загрузки и ложного увеличения площади |
| PHYS-13 | Save/restart и loaded↔virtual | Одинаковая учтённая площадь, один слот/гражданин |
| PHYS-14 | Подмена результата клиентом | Сервер отклоняет неподтверждённую пригодность |
| PHYS-15 | Достаточно безопасного пола/кроватей, но меньше 4 блока² на NPC | Применяется предварительный D-056 без дополнительного «бонуса» от частичного блока, если его площадь не утверждена |

## 7. Следующее проектное решение

**Выбран CELL (D-058):** каждая уникальная физически пригодная и проходимая клетка даёт ровно **1 блок²**. Дробные площади по частичным блокам не начисляются. Нормализация поверхностей, двойной учёт этажей и алгоритмы всё ещё PROPOSED. Для P1 важны воспроизводимые расчёты, проверка лестниц/плит и отсутствие дробных эксплойтов.
