# P1 — CELL: целочисленный учёт пригодных клеток пола

**D-058 APPROVED_CONCEPT, 2026-11-18.** Каждая **уникальная** клетка пола, прошедшая физическую проверку PHYSICAL (D-057), даёт **ровно 1 блок²** пригодной площади жилья. Частичная площадь внутри засчитанной клетки не вычисляется. Все детали распознавания и принадлежности клеток ниже — **PROPOSED / NOT FROZEN**.

## 1. Цепочка принятых ограничений

- D-053 ROOM: физическая кровать, укрытие, доступ, безопасность и законное размещение.
- D-054 COMBINED: одновременно ограничивают кровати и площадь, комфорт — отдельно.
- D-055 FLOOR: площадь пола, не 3D-объём.
- D-056: предварительно **4 блока² на NPC**.
- D-057 PHYSICAL: действительная опора, проходимость, доступность, безопасность, даже для плит/ступеней.
- **D-058 CELL:** одна прошедшая проверку клетка = **1 блок²**, а не дробное число; одна и та же физическая клетка учитывается ровно один раз.

## 2. Как игроку засчитывается площадь

| Поверхность | Результат |
|---|---|
| Полный блок, безопасный и достижимый | +1 клетка |
| Плита, на которой NPC может безопасно находиться и до которой может дойти | +1 клетка |
| Ступень при тех же условиях | +1 клетка |
| Плита, ступень или полный блок без прохода/безопасности | 0 |
| Ковёр поверх той же поверхности | Без второй клетки |
| Две части составного блока, создающие одну и ту же позицию опоры | Не дублировать |
| Изолированный этаж/антресоль без пути NPC | 0 для жилища |
| Реальный другой этаж, к которому есть безопасный путь | Может давать дополнительные **отдельные** клетки, не копии первого этажа |

**Открытый вопрос:** как нормализовать `SurfaceKey` для нестандартных коллизий, когда внутри одного (x,z) существуют несколько непересекающихся ходовых уровней по Y. Правило: не допустить двух начислений одной и той же полезной поверхности; фактически отдельные этажи могут учитываться, если они одновременно пригодны и достижимы.

## 3. Модель расчёта для P1 (предложение реализации)

1. Найти валидный ROOM вокруг канонической кровати.
2. Собрать множество физических клеток пола по PHYSICAL с определённой принадлежностью помещению.
3. Нормализовать `FloorCellId = (WorldId, DimensionId, X, Y, Z, canonicalSurfaceKey)` — структура **кандидат**, не готовая схема.
4. Удалить дубликаты из ковров/составных блоков/повторных событий и клеток, уже закреплённых за другой жилой областью.
5. Подсчитать `usableFloorCellCount` как целое неотрицательное число.
6. Для предварительного D-056 применить `housingCapacity = min(usableBeds, floor(usableFloorCellCount / 4))`, если ROOM валиден и права позволяют новое заселение.
7. Не превращать излишнюю площадь в дополнительные кровати; `ComfortScore` считать отдельно.

**Сервер — единственный источник истины**. При изменении блока пересчитывается только затронутая область, с защитой от устаревших ревизий. Выгруженные необходимые чанки или превышенный лимит обхода дают `PENDING_VERIFICATION`, а не придуманную площадь.

## 4. Подсчёт примерных домов

| Пригодные клетки | Кровати | Максимум NPC |
|---:|---:|---:|
| 3 | 1 | 0 |
| 4 | 1 | 1 |
| 7 | 2 | 1 |
| 8 | 2 | 2 |
| 11 | 3 | 2 |
| 12 | 3 | 3 |
| 20 | 2 | 2 |

Каждая строка предполагает валидные ROOM, права на заселение и действительную физическую пригодность клеток. Норма 4 — предварительный баланс.

## 5. Границы механики и производительности

- **Коллизии прежде учёта:** определение «клетка пригодна» нельзя заменить whitelist блоков.
- **Не суммировать половинки:** две половины slab или подложенный ковёр не становятся двумя клетками.
- **Без двойного назначения:** `FloorCellId` принадлежит не более чем одной жилищной области при расчёте лимита. Общие комнаты/коридоры требуют отдельной политики разделения.
- **Реальные этажи:** для совпадающих X/Z, но независимых Y, нужен проверенный маршрут, реальная опора и корректная принадлежность.
- **Без постоянного полного сканирования:** перепроверка по событиям, ограниченный поиск, сохранённая ревизия и осторожный результат при неопределённости.
- **Обновление правил:** версия алгоритма подсчёта — часть persistence/migration; после обновления не удалять NPC или здания автоматически.
- **Только housing-area:** подсчёт не выдаёт NPC, не увеличивает денежную казну, не влияет напрямую на производство/исследования.

## 6. Проверки CELL-01…14 (для будущей реализации)

| ID | Сценарий | Ожидаемо |
|---|---|---|
| CELL-01 | Одна безопасная достижимая клетка из полного блока | Ровно 1 блок² |
| CELL-02 | Одна пригодная плита | Ровно 1 блок², не 0.5 |
| CELL-03 | Одна пригодная ступень | Ровно 1 блок² при успешном PHYSICAL |
| CELL-04 | Одна физически недоступная плита | 0 |
| CELL-05 | Ковёр над пригодной клеткой | По-прежнему 1, не 2 |
| CELL-06 | Двойное событие изменения составного блока | Только одна клетка/учёт |
| CELL-07 | 3 клетки + 1 кровать | 0 жилых мест по предварительной норме |
| CELL-08 | 4 клетки + 1 кровать | 1 место |
| CELL-09 | 7 клеток + 2 кровати | 1 место |
| CELL-10 | 8 клеток + 2 кровати | 2 места |
| CELL-11 | Два реально доступных этажа на разных Y | Независимые клетки; без удвоения одного этажа |
| CELL-12 | Две комнаты претендуют на общую клетку | Не более одного учёта площади |
| CELL-13 | Save/restart и переход loaded↔virtual | Результат и назначения не дублируются |
| CELL-14 | Отсутствующий чанк, конфликт ревизии или превышен бюджет | Нет ложного увеличения площади |

## 7. К чему переходить дальше

D-053…D-058 образуют согласованную концептуальную цепочку жилья. **Дальше важно проектировать общую территорию и многокомнатные дома**, а не по одной выбирать тип блока: что считать самостоятельной комнатой, как распределять общий коридор/лестницу, какие этажи относятся к конкретному жилью и кто разрешает заселение. Отдельно остаются численная оценка комфорта, точные правила опасности и бюджет проверок.

Проектная спецификация подготовлена: [P1 Housing Regions / Shared Space](P1_HOUSING_REGIONS_AND_SHARED_SPACE_PROPOSAL.md). Три способа распределения общего пространства (PRIVATE_ONLY, SHARED_ALLOCATED, COMPLEX_POOL) остаются **PROPOSED**, ни один не утверждён автоматически.
