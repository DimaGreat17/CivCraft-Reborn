# P1 — HYBRID: материалы и функциональные блоки модульных зданий

**Статус:** выбор материалов HYBRID утверждён как концепция D-052 (2026-11-18). Остальные технические детали — PROPOSED / NOT FROZEN.  
**Контекст:** D-049 (центральный блок), D-050 (функциональные здания по чертежам, дома и декор свободно), D-051 (MODULES), D-052 (vanilla-конструкции + специальные блоки для уникальных функций). Никакой игровой код в P0 не затрагивается. P1 не реализуется до приёмки P0 и отдельного разрешения.

## 1. Утверждённая граница

Конструктивные и декоративные части модульного здания разрешено строить из обычных блоков Minecraft. Мод добавляет собственные блоки **только для уникальных функций, которые не покрываются стандартными блоками**. Функция существует, лишь когда необходимые модули физически размещены, проверены сервером, доступны по правам и обеспечены входными ресурсами/трудом.

Это **не** решение делать все функциональные элементы новыми блоками. Также оно не разрешает считать случайную vanilla-конструкцию готовым производственным объектом без утверждённого чертежа и валидации.

## 2. Разделение материалов (проектный контракт)

| Категория | Возможное воплощение | Правило |
|---|---|---|
| Несущая/ограждающая конструкция | Vanilla-блоки из разрешённых тегов | Игрок меняет стиль, сохраняя границы/доступ и минимальную физическую целостность |
| Декоративная отделка | Vanilla-блоки и разрешённые декоративные модовые варианты | Не даёт бесплатных экономических бонусов |
| Хранение/обычное взаимодействие | Vanilla-контейнеры, если их возможностей достаточно | Подключение к реальному физическому инвентарю, с правами доступа; не создавать параллельный «виртуальный» товар |
| Специальная функция CivCraft | Специальный функциональный блок мода, **только при обоснованной необходимости** | Серверный BlockEntity/состояние или иной адаптер с правами, версией и валидируемой функцией |
| Модуль доступа | Физически достижимый вход/рабочая позиция | Ни рабочий NPC, ни игрок не используют недоступный модуль через UI |

Набор конкретных тегов, рецептов и классов блоков не утверждён. Слова «несущая» и «целостность» обозначают проверяемые требования чертежа, а не новую физику Minecraft.

## 3. Критерии добавления специального блока (предложение)

Перед добавлением каждого нового блока:
1. Назвать требуемую игровую функцию и источник (legacy CivCraft или оригинальное расширение Reborn).
2. Проверить, можно ли реализовать её через существующий vanilla-блок плюс зарегистрированный серверный модуль/контроллер.
3. Если vanilla-варианта недостаточно, обосновать новый блок, его границы владения, рецепты, события и сохранение.
4. Подтвердить, что блок не создаёт дополнительные предметы без работы, расхода и единственного журнала операций.
5. Добавить тесты разрушения, переноса, повторного размещения, загрузки мира, конфликтов и доступа NPC.

**Примеры для обсуждения, не утверждённый каталог:** центральный блок лагеря (уже утверждён D-049), управляющий интерфейс производственного процесса, специализированная станция с уникальной механикой CivCraft. Не утверждать новые «склады», «генераторы ресурсов» или аналоги без отдельного проектирования.

## 4. Операции и валидация

Предлагаемый контракт:
- `StructuralModule`: допустимые vanilla block tags, допустимая геометрия/ориентация, точки связи.
- `FunctionalModule`: `ModuleId`, тип функции, `BlockRef`, допустимый vanilla/custom вариант, права использования.
- `BlueprintInstance`: `BlueprintId`, `BlueprintVersion`, `ConstructionId`, набор обязательных модулей и ревизия проверки.
- `ValidationResult`: отсутствующие/повреждённые модули, конфликт геометрии, доступа/прав, материалов и производственных требований; причины понятны игроку.

Сервер выполняет проверки по реальным состояниям блоков. Клиент отправляет действие, но не диктует результат. Для дорогостоящей проверки нужна событийная инвалидизация и ограниченный пересчёт, а не полный скан всех домов каждый тик. При недоступном чанке нельзя без доказательств активировать новую физическую структуру. Дальняя симуляция опирается на подтверждённое сохранённое состояние и одинаковые затраты с локальной.

## 5. Строительство и жизненный цикл

1. Игрок размещает модульный чертёж и выбирает разрешённые ванильные варианты элементов.
2. Реальные блоки доставляются и ставятся им или NPC; материалы нельзя списать дважды.
3. Специальный функциональный блок добавляется только там, где он требуется утверждённым конкретным чертежом.
4. После серверной проверки здание становится активным и может выполнять только реально обеспеченную функцию.
5. Изменение внешнего вида не влияет на функцию, если обязательные модули и доступ сохранены.
6. Уничтожение функционального блока останавливает соответствующую функцию; блок не должен возрождаться после перезагрузки.
7. При изменении схемы/типа блока применяется явная миграция, а не молчаливое переписывание пользовательских построек.

## 6. Границы свободного дома

Свободно построенные обычные дома и декор по D-050 не требуют чертежей. **ROOM (D-053) утверждён как принцип:** пригодность свободного дома для NPC автоматически проверяется по кровати, укрытию, доступу и безопасности. Конкретная геометрия, пороги и алгоритмы пока открыты; подробнее: [ROOM housing](P1_ROOM_HOUSING_RECOGNITION_CONTRACT.md). Не привязывать право игрока строить дом к обязательному модовому блоку без нового решения.

## 7. Двенадцать дополнительных проверок

| ID | Проверка |
|---|---|
| PHYB-01 | Разные разрешённые vanilla-материалы дают эквивалентное базовое здание при одинаковых обязательных модулях |
| PHYB-02 | Отсутствующий специальный функциональный блок при обязательности не позволяет активировать функцию |
| PHYB-03 | Наличие специального блока без требуемых модулей/доступа само по себе не активирует здание |
| PHYB-04 | Смена отделки без изменения обязательных модулей не останавливает рабочую функцию |
| PHYB-05 | Vanilla-контейнер и реестр запасов не дублируют содержимое |
| PHYB-06 | NPC не может использовать функциональный модуль вне доступа или чужих разрешений |
| PHYB-07 | Разрушение/потеря функционального блока ведёт к корректному состоянию повреждения |
| PHYB-08 | Перенос функционального блока не переносит автоматически права, историю или оплаченные ресурсы |
| PHYB-09 | Сервер отвергает клиентское сообщение «здание готово», если физические блоки отсутствуют |
| PHYB-10 | После crash/reload сохраняются валидные модули и не дублируются предметы/производство |
| PHYB-11 | Обновление версии схемы не заменяет чужие vanilla-блоки автоматически |
| PHYB-12 | Свободно построенные дом и декор не требуют схемы и не получают случайных производственных эффектов |

## 8. Следующее проектирование

1. Каталог первоначальных функциональных объектов P1 и решение, где действительно необходим собственный блок.
2. Универсальные группы допустимых vanilla-блоков, ограничения геометрии и критерии ремонта.
3. Автоматическое распознавание свободных домов ROOM утверждено как принцип (D-053); геометрия, безопасность, доступ и правила заселения требуют согласования.
4. Интерфейс выбора варианта материала и визуализация обязательных модулей.
5. Рецепты, стоимости, длительности, вместимости и права — отдельно утверждаемый баланс.
6. Версионирование и миграции BlockEntity/схем на сервере; нагрузочные испытания.
